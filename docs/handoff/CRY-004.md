# CRY-004 — Data source health

## Summary

Each market and news feed now records its last successful update, error count,
latency, and a status: `fresh`, `degraded`, `stale`, or `erroring`. Status
changes are written to the structured log (`source_health` and
`source_health_changed`). The same snapshot is returned by
`GET /integration/v1/health` and included on `GET /health` under `data_sources`.

A feed is stale after three missed polls of its own interval (never sooner
than 30 seconds). It is degraded when the last fetch was slower than
`source_health_degraded_latency_ms` (default 5000), when at least half the
symbols failed, or when it has consecutive errors below the erroring
threshold. It is erroring after `source_health_error_threshold` consecutive
failures (default 3).

The existing Telegram notifier is the notification hook. It sends only when
`source_health_notify_enabled` is true, and only when a feed enters
degraded, stale, or erroring, or returns to fresh. The flag defaults to false.

## Assumptions

- `/integration/v1/health` was not in the repo. It is a new read-only GET,
  public in the same way as `/health` (the rate limiter only covers `/api/`).
  `GET /health` still returns `"status": "ok"` when a feed is bad, so a stale
  upstream does not fail the process liveness check. Feed rollup is
  `data_sources.status` on `/health` and `status` on `/integration/v1/health`.
- Stale is per feed: three times the poll interval (`binance_klines_seconds`,
  `delta_klines_seconds`, CoinGecko, CoinDCX, CryptoPanic), three times the
  Fear & Greed refresh, and 15 minutes for RSS and news collectors (their
  jobs run every 5 minutes). Feeds with no known interval use
  `source_health_stale_after_seconds` (default 180).
- A feed that has never succeeded is degraded until it hits the error
  threshold, then erroring. One error after a recent success is degraded,
  not erroring.
- CryptoPanic with no token is not recorded. An empty watchlist is a
  successful poll, not an outage.
- Status changes are logged at warning, not error, so the existing
  error-to-Telegram processor does not page on feed health. The dedicated
  hook is the only notifier, and it is off by default.
- No new dependency.

## Known gaps

- WebSocket streams (`delta_ws`, `binance_ws`, Twelve Data) are not sampled.
  A record on every tick would sit on the live price path. Delta and Binance
  candle polls are tracked.
- A collector that is switched off never appears. It is not labelled
  `disabled`.
- A fetch whose latency sits on the 5000 ms line can flip between fresh and
  degraded. Notifications, if turned on, would follow each crossing.
- The five paper-trading failures above are the NFP blackout on this clock,
  not a regression from this branch.

## Security impact

Read-only. No orders, no broker or exchange writes, no live trading, no new
secrets. Error text is passed through `analysis.news.sanitize.sanitize_error_message`
before it is stored or handed to the notifier, so query strings (API tokens
in URLs) are not copied into the health payload or the Telegram text.
`/integration/v1/health` and `/health` are unauthenticated, matching the
existing liveness route. The notify flag defaults to false.

## Rollback

new package. Unset `SOURCE_HEALTH_NOTIFY_ENABLED` if it was turned on.
The new route disappears with the revert; `/health` returns to the previous
body.
